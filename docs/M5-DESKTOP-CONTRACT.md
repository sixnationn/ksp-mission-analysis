# M5 desktop workflow contract

Specified before implementation. The GTK application is an external mission-analysis tool, not an in-game editor. Ubuntu is the primary target; Windows is required. It must show source identity, confidence, frame, force model and ephemeris coverage wherever a trajectory is presented. An M1 raw/provisional catalog can be inspected but cannot start a dated search until a complete state snapshot is loaded. A synthetic demonstration must say synthetic in the window and saved report.

## First observable slice

Open a versioned runtime JSON snapshot, validate it and its exact-byte SHA-256, display a body table with SI units and the no-leap calendar, and show a 3D barycentric scene from the same state. Invalid JSON, missing body state, unsupported frame, absent Principia provenance, unknown atmosphere, and a mismatched source hash must produce visible errors without a partial analysis-ready state. For an initial milestone, the scene may draw simple body markers and orbit-path samples without textures; camera orbit, pan, zoom and body selection must be usable. Camera-relative coordinates protect rendering precision at planetary distances. Changing camera state must not alter simulation state.

The mission panel names home, Mars-role, Venus-role and central bodies from imported IDs, plus launch window, flight times, stay duration, parking/capture altitudes, flyby clearance and return condition. The requested parking-orbit stay is exactly 5,184,000 SI seconds; game calendar days are separately displayed. Invalid role mappings or ranges block search with a clear reason. The GUI launches a separate numerical worker with a versioned request and progress protocol; it does not run heavy search on the GTK main thread. Cancellation terminates or asks the worker to stop, retains already accepted candidates, and leaves the window interactive. A checkpoint identifies snapshot hash, mission request, solver settings and candidate set so incompatible resumes are rejected.

The candidate table distinguishes a fast screened seed from an independently refined feasible route. Selecting a candidate draws dated arcs, encounter markers and distinct burn markers. The report records separate injection, capture, departure and correction delta-v, C3 convention, constraint margins, unresolved events, force model, source confidence and exact snapshot hash. Save and reload must preserve these labels and numbers. A viewport screenshot at normal desktop size, cancellation during a real benchmark workload, save/reload, and Ubuntu/Windows native builds are acceptance evidence. A compile or synthetic test alone is not rendered acceptance.

## Initial GTK window slice

The first standalone GTK slice may be a data-driven window using a synthetic M2 fixture: left source/body list, central 3D scene, right mission fields, bottom candidate/progress area. It must label all values synthetic and keep search/export actions disabled until a worker and validated runtime snapshot are wired. The design uses restrained dark neutrals, crisp typography, aligned data columns and explicit units. It should avoid decorative dashboard chrome that competes with the trajectory. This slice is not M5 completion.
