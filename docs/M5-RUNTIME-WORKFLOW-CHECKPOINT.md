# M5 runtime mission workflow checkpoint

The GTK window now builds a `start_mission` request only after an exact-byte runtime JSON has been imported. The right-side form accepts exact body IDs, SI-second launch and three flight grids, parking/capture altitudes, flyby constraints, ephemeris settings, and bounded work/route limits. The worker runs outside GTK; the window polls validated events, shows progress and final ranked four-burn screened routes, and offers cancellation. A completed result can be saved as a versioned historical JSON study. Report composition reopens and rechecks the runtime source bytes against the original SHA-256, records the no-leap display calendar, and rejects source or request mismatches. Synthetic display data cannot start a mission search.

The submitted request and terminal event are separate from the on-screen preview. The saved result is labeled `patched_conic_screen_only`, and source confidence remains `runtime_observed_uncompared`. The source file is required again to rerun. Report tests first failed because composition was absent; after implementation, the headless Windows report executable passed 30 checks, and the full MSYS2 UCRT64 CTest suite passed 11/11. All six native Ubuntu and Windows jobs passed in [CI run 35797442290](https://github.com/sixnationn/ksp-mission-analysis/actions/runs/35797442290). The GTK target compiled headlessly, and the missing-source `--validate-snapshot` path rejected input without opening a window. No GTK or KSP window was launched during this checkpoint because the requested desktop placement could not be guaranteed.

Rendered layout, worker responsiveness while the window closes, interactive save behavior, and an actual JNSQ Reborn Real Principia runtime export remain unverified. The screened route is an optimistic seed and does not establish a feasible integrated multi-leg trajectory or a playable flight plan.
