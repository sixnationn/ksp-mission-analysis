# Fixed-impulse trial in the GTK workflow

The runtime mission form gains an explicitly labeled **fixed-impulse trial JSON path** and **Evaluate fixed trial** action. This is an advanced, user-supplied trial, not an optimizer or an automatic conversion from a screened route. The trial JSON must be an object accepted by the existing worker's `trial` schema. The desktop constructs protocol-v1 `evaluate_route` with the currently imported exact runtime source path/hash, inertial frame, state epoch and a new request ID; it never accepts source identity or atmosphere data from the trial file. The trial file read is capped at 1 MiB. Source path/hash changes since import, malformed/oversized trial JSON, duplicate active worker, missing runtime import, and invalid timeout fail visibly before starting a process.

The evaluation action uses the validated `fixed_impulse_evaluation` WorkerClient mode. Started/progress/complete/cancelled/error update the same nonblocking worker area. Evaluation progress is phases 0/1 rather than Lambert cells. A completed result displays the four charged burns, four named checkpoint residuals, Venus clearance and safety margin, Mars radius range, strict-pass disagreement and the exact partial-result label. It displays both evidence flags as false and calls the result **checkpointed trial**, never feasible, optimized or Principia-verified. Cancellation or error cannot enable export. Switching sources clears a previous trial result and retained event stream. The screened mission action and report behavior continue unchanged.

The save action writes a completed evaluation through the dedicated self-contained evaluation-report composer, including exact runtime bytes, submitted request and observed event stream. A report failure leaves any previous destination intact. Screened mission reports retain their existing format. Before implementation, confirm the current form's evaluation path fails because it has no action and the existing progress/result/report code assumes `start_mission`; after implementation, focused headless report tests plus Ubuntu/Windows GTK compilation verify the wiring. Rendered review and UI responsiveness under a real numerical workload remain separate M5 gates because project windows cannot be placed on the requested desktop headlessly.
